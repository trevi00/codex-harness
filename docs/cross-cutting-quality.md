# 공통 품질 시나리오와 설계 검수

2026-09-08 사용자 요구. 화면·백엔드·하네스·컨텍스트 관리에 공통 적용한다.
이 문서 등록은 측정기나 강제 게이트의 구현 완료를 의미하지 않는다.
[지휘자 평가 계약](conductor-evaluation.md)의 version/scope/window/evidence/status 구조를 따른다.
미측정은 unknown이며 임의 종합 점수나 인증을 만들지 않는다.

| ID / 기준 | 검증할 시나리오 | 근거 |
| --- | --- | --- |
| Q-USE / 사용성 | 사람이 실제 목표를 수행하고 오류에서 회복할 수 있는가 | 핵심 여정의 완료·오류·도움 요청 관측, 사람 인수 검토 |
| Q-INT / 직관성 | 실행·대기·차단·미측정·승인과 실제 배포를 혼동하지 않는가 | 상태 해석 과제, 문구/정보 구조 검토, 원본 증적 접근 |
| Q-REL / 안정성 | 연결/저장/도구 실패·중복·재시작·오래된 관측에도 거짓 성공이 없는가 | 장애 재현·정상 대조군·복구/카나리아 기록 |
| Q-EXT / 확장성 | 팀·기기·스택·지표·시나리오 추가가 공통 정책 복제로 이어지지 않는가 | 확장 변경의 영향 범위, 포트 계약과 호환성 검사 |
| Q-COH / 응집도 | 한 모듈이 한 책임/변경 이유에 집중하고 있는가 | 데이터 소유권·use case·모듈 책임/변경 이력 검토 |
| Q-COUP / 결합도 | 외부 도구/SDK/저장소 변화가 내부 정책까지 전파되는가 | import 경계, 의존 순환, 변경 영향 그래프, 어댑터 교체 검증 |
| Q-MAINT / 유지보수성 | 결함을 재현하고 근거를 찾고 안전하게 수정·복구할 수 있는가 | 재현 절차, 테스트/계약 추적, 변경 lead time, 재발과 운영 복구 |

각 후보는 적용 항목·기준 버전·비교 대상·실행 결과·미확인 사항을 검수 보고서에 남긴다.
수치 목표는 실제 baseline과 제품 요구에 따라 정한다. source label만으로 국제 기준
준수라고 하지 않는다. 적용 불가는 범위와 이유가 필요하다.

SOLID는 클래스를 늘리기 위한 규칙이 아니다. SRP는 정책/조회 projection/HTTP/표시를
분리하고, OCP는 Device/로그/메시지 port의 어댑터 추가로 확장한다. LSP는 성공뿐 아니라
실패·취소·timeout·evidence 의미가 공급자 교체에도 유지되는지 확인한다. ISP는 observe,
interact, lease, evidence 등 필요한 최소 기능으로 나눈다. DIP는 application/domain이
SDK나 UI에 의존하지 않고 port에 의존하도록 한다. 순수 함수가 적합한 정책은 그대로 둔다.

패턴은 검증 가능한 문제에만 적용한다: Adapter/Strategy(공급자와 실행 정책),
State Machine(작업·검수·배포), Repository/Unit of Work(상태 소유권/트랜잭션),
Outbox(상태와 전달 의도), Observer(표시 갱신), Builder(컨텍스트 조립).
각 도입은 해결 문제·대안·비용·실패 의미를 ADR/계약에 연결한다. 기본 클래스 계층과
패턴 수를 품질 점수로 사용하지 않는다.

컨텍스트 관리는 수집·선택/순위·예산·직렬화·인계를 분리하고 불변 evidence refs와
generation을 전달한다. 선택하지 못한 항목/이유를 기록하고 파생 요약을 SSOT로 승격하지
않는다. 수집기가 바뀌어도 의미·예산·누락·오래된 근거 처리 계약이 보존되어야 한다.

모니터 VIEW는 모션을 상태 신호로만 쓰며 완료/성과를 연출하지 않는다. 모션 감소,
키보드 탐색, 작은 화면, stale/unavailable, 빈 기록을 검증한다. 보고서는 배포 포인터와
정확히 일치한 릴리스만 연결하고, 기록된 검수 결과와 지금 재검증한 사실을 구분한다.
현재 보고서에는 기능/파일 diff·원문 증적 무결성·7개 품질 축의 종합 실측이 없으며,
이들을 추가하기 전에는 상세 기록 요약을 완전한 배포 인증 보고서라고 부르지 않는다.
